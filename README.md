# 4797_model

Code for **Hierarchical Computational Mechanisms of Social Cue Integration in Autism: A Bayesian Modelling Approach** (PN4797 research project).

The repository contains the full analytic pipeline:

1. **Data cleaning** — Python scripts that turn raw Gorilla CSV exports into trial-level, HGF-ready CSVs and a participant metadata table.
2. **HGF model** — MATLAB implementation of four candidate perceptual architectures (A, B, C, M4) plus three initial-condition (I1) variants, fitted via variational Bayes and compared with random-effects Bayesian Model Selection.
3. **Analysis** — group comparisons (ASD vs NT), demographic equivalence, sensitivity analysis, condition-stratified AQ correlations, and the publication figures.

For the full mathematical specification, the file-to-component mapping, and a step-by-step table of which script produces which output, see [`MODEL.md`](MODEL.md).

Notes on what ships:
- `data/raw_gorilla/` is **git-ignored** because the raw exports contain Prolific Public IDs.
- `data/pid_lookup_PRIVATE.csv` is **git-ignored and never released**. It exists only on the author's machine so that the author retains the ability to re-identify participants if needed (e.g., a withdrawal request). The repo intentionally distributes no auxiliary group/condition file derived from the Prolific export.
- `data/cleaned/`, `data/participant_metadata.csv`, `data/quality_report.csv`, `data/cleaning_report.txt` are **shipped** as anonymised (`P###`) files so anyone who skips the cleaning step can run the MATLAB pipeline directly.
- The single source of truth for `ASD` vs `NT` group membership — and for AQ, DASS, FI, condition, demographics — is `data/participant_metadata.csv`. Every MATLAB analysis script joins on `participant_metadata.participant_id` to obtain those labels.
- `hgf_model/results/`, `hgf_model/results_I1/`, `hgf_model/results_stratified/` are git-ignored (large; regenerated by MATLAB).

## Two ways to run

The bundle distributed in this repo (everything under `data/` except `raw_gorilla/` and `pid_lookup_PRIVATE.csv`) is **already anonymised**: every Prolific Public ID has been replaced with a stable `P###` label (`P001`, `P002`, …). All MATLAB scripts treat the participant ID as an opaque string, so the anonymised bundle is functionally identical to the un-anonymised one.

There are two equivalent entry points:

- **Path A — Skip cleaning, run MATLAB only.** Use the anonymised CSVs that ship with the repo (`data/cleaned/*.csv`, `data/participant_metadata.csv`, `data/quality_report.csv`). Jump straight to step 4.
- **Path B — Re-run from raw Gorilla exports.** Requires the raw exports to be obtained separately under the project's ethics agreement (request via the supervisor). Anonymisation is then performed automatically as part of step 3.

All commands are run from the repository root.

### 1. (Path B only) Place the raw data

A Gorilla "Combined Data" download for experiment 259923 arrives as a single folder called `data_exp_259923-vall/` containing 16 CSVs — five `questionnaire-*` files (consent, demographics, AQ50, DASS21, an extra debrief sheet) and eleven `task-*` files (one per Gorilla node, including the Fluid Intelligence adaptive test `task-6hny` and ten versions of the main facial-verbal task). The cleaner reads them flat from `data/raw_gorilla/`, so just **drop the whole Gorilla folder under `data/` and rename it to `raw_gorilla`**:

```bash
mv /path/to/data_exp_259923-vall  4797_model/data/raw_gorilla
```

(or, if you prefer to keep the Gorilla folder where it is, copy the CSVs across with `mkdir -p data/raw_gorilla && cp /path/to/data_exp_259923-vall/data_exp_259923-vall_*.csv data/raw_gorilla/`).

After the move, `data/raw_gorilla/` should contain these 16 files at one level deep:


### 2. Install Python dependencies

```bash
pip install -r requirements.txt
```

(Path A can skip this — Python is only needed for cleaning.)

### 3. (Path B only) Clean the data (Python)

```bash
python data_cleaning/comprehensive_cleaning_pipeline.py
```

This produces, all under `data/`:
- `data/cleaned/<P###>_cleaned.csv` and `data/cleaned/<P###>_hgf_input.csv` for each participant
- `data/participant_metadata.csv` (group, AQ50 total + 5 subscales, DASS21, FI, condition, demographics)
- `data/quality_report.csv` (per-participant accuracy, follow-rates, RT, timeouts, calibration)
- `data/cleaning_report.txt` (run summary)
- `data/pid_lookup_PRIVATE.csv` (Prolific ↔ `P###` mapping; **git-ignored, never released**)

The `P###` labels are assigned deterministically: PIDs are sorted alphabetically and numbered. If the lookup file already exists from a previous run, existing assignments are preserved and only new PIDs are appended — re-running the pipeline therefore produces identical filenames.

**Group columns and canonical-label override.** The pipeline emits two group columns:

- `selfReportGroup` — output of the automatic rule (`asc_diagnosis == 'yes'` → ASD, AQ ≥ 32 → NT_highAQ, else NT). Always reproducible from raw data alone.
- `group` — the **canonical analytic label** (`ASD` / `NT`) used by every MATLAB analysis. The auto-rule does **not** reproduce these labels because the project's group assignment was hand-curated on top of Prolific recruitment data (see report); a few participants are recoded between ASD / NT / NT_highAQ relative to the auto-rule.

To preserve the curation across re-runs, the pipeline does the following: after computing the auto-rule labels, it checks for an existing `data/participant_metadata.csv`. If found, it reads that file's `group` column and overwrites the freshly computed `group` for every matching `participant_id`, then writes the merged result straight back to the live file. Participants in the new run that are not in the existing curated file get the auto-rule label and are listed in the console for review. The shipped `participant_metadata.csv` (which is what `git clone` gives you) therefore acts as the source of truth — re-running cleaning will reproduce the canonical labels rather than overwrite them with the auto-rule.

(Optional) re-run only the trial-level part for a single participant:
```bash
python data_cleaning/data_cleaning_pipeline.py data/raw_gorilla/data_exp_259923-vall_task-gsep.csv
```
or batch-rebuild trial-level files using the existing metadata:
```bash
python data_cleaning/run_all_cleaning.py
```
These two helpers operate on whatever ID is in the raw CSV they are given, so they are intended for debugging on the raw export only — the canonical anonymised pipeline is `comprehensive_cleaning_pipeline.py`.

### 4. Set up MATLAB

Open MATLAB and `cd 4797_model/hgf_model`. `MLTM_options_new.m` adds all model sub-folders to the MATLAB path automatically when invoked, including the bundled `hgf_model/spm/` (which contains `spm_BMS` and its dependencies). No separate SPM12 download is required.

### 5. Fit the four candidate architectures (MATLAB)

```matlab
cd('hgf_model')
MLTM_main_new
```

This runs:
- **First level** — variational-Bayes inversion of the four perceptual models × softmax response model for every subject; outputs `<resultroot>/<subjID>_<prc_config>_<obs_config>.mat`.
- **Second level** — BMS with `spm_BMS`, identifiability check on the per-subject posterior correlations, MAP parameter extraction (`MLTM_MAP_estimates.csv`), and the group comparison plots.

> **A note on BMS reproducibility.** `spm_BMS` uses Gibbs sampling for the exceedance probabilities, so re-running the second-level step will produce slightly different `xp` values from one run to the next (typically within ≤1 percentage point of the values printed in the manuscript). The posterior expectations `⟨r_m⟩` are analytic and are stable across runs. The model ordering is unchanged. If you need bit-exact reproduction of the manuscript Table 2 numbers, save the relevant `BMS_results.mat` from a single run; otherwise, expect this small Gibbs fluctuation.

### 6. Initial-condition variants (optional)

```matlab
MLTM_main_I1
MLTM_I1_analysis        % run after BMS shows whether an I1 variant wins
```

Saves to `hgf_model/results_I1/`.

### 7. Parameter recovery and identifiability diagnostics

```matlab
MLTM_parameter_recovery               % simulation–recovery on the winning model
MLTM_laplace_kappa_theta(MLTM_options_new())   % κ↔θ posterior correlations
```

### 8. Group comparisons, AQ correlations, sensitivity (MATLAB)

```matlab
cd('../analysis')
MLTM_sample_characterisation
MLTM_demographics                 % demographics + clinical + behaviour (Table 1 territory)
MLTM_stratified_AQ_analysis       % Table 5
MLTM_sensitivity_analysis         % outlier-excluded re-run
```

These analysis scripts read **only** `participant_metadata.csv` and `quality_report.csv` (and, for the AQ-stratified analysis, the MAP-estimate CSVs already produced in step 5). All AQ50 totals + 5 subscales, DASS21 subscales, FI scores, age, gender, and behavioural metrics (accuracy, follow-rates, RT, calibration) are pre-computed during cleaning and stored as columns of these two files — the questionnaire-level Gorilla exports are not needed at this stage.

The model parameter Group × Condition ANOVA that produces **Table 4** (`hgf_model/MLTM_group_comparison.m`) runs automatically as the last step of `MLTM_main_new`. To re-run it on its own:

```matlab
cd('../hgf_model')
MLTM_group_comparison(MLTM_options_new())
```

All values in the report's Tables 1–5 and the sensitivity analysis are produced by the MATLAB scripts above. Python is used **only** for the data-cleaning pipeline in `data_cleaning/`.

## Notes on the model

Per cue stream, a three-level binary HGF tracks (1) the trial outcome (Bernoulli with sigmoid mean), (2) the cue-accuracy belief (Gaussian random walk modulated by Level-3 volatility through coupling κ), and (3) phasic volatility (Gaussian random walk with step variance ϑ).

Architectures differ in how the three facial **equivalence groups** (EG A/B/C, with HIGH/LOW accuracies 70/10, 80/20, 90/30) are represented:

- **Arch A** (`hgf_binary3l_facial_verbal`) — single facial HGF (full generalisation across EGs).
- **Arch B** (`_archB`) — three independent facial HGFs sharing κ_f, ω_f, ϑ_f.
- **Arch C** (`_archC`) — shared Level-3 volatility, separate Level-2 accuracy beliefs per EG.
- **M4** (`_gamma`) — Arch A plus a free generalisation strength γ ∈ [0,1] applied at Level 2:

  > μ₂_f(k) = μ̂₂_f(k) + γ · π̂₂_f(k)⁻¹ · δ₁_f(k)

The response model integrates facial and verbal beliefs with bias ζ and inverse temperature β symmetrically modulated by Level-3 volatility on both streams (β_eff = β · exp(−μ̂₃_f − μ̂₃_v)).
